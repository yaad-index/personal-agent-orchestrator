# ADR 0043: The memory driver, storing and retrieving what an agent or template remembers

**Status:** Accepted (2026-11-25)

## Context

ADR-0039 named memory as driver plane 2, and noted pao has no memory of its own today. ADR-0041 made a template carry persistent memory and deferred to this ADR whether that memory is per-user or shared, leaving the binding of a template's memory to the tag-as-capability ADR that follows.

This ADR draws plane 2: how memory is stored and retrieved, how it is keyed and scoped, and what the first backend is. It follows ADR-0039's plane discipline, a narrow interface, a simple first implementation, and a contract test.

## Decision

1. **Memory is reached through a narrow driver, keyed by tag within an accessible namespace.** The memory plane (ADR-0039 plane 2) is a driver that stores and retrieves what an agent or template should remember. Access to memory is decided by the **namespace**, which is the access-controlled resource granted under ADR-0012. A **tag** is the **retrieval key used within the namespaces the reader is already granted**: it selects which memories to return and does not itself reach across a namespace boundary. So a tag match never returns memory from a namespace the reader has no grant on, which keeps ADR-0012 point 3's tag-as-scope from silently reaching private memory through the key. The tag's definition as the capability primitive is the next ADR's subject; here it is only the key that filters inside granted namespaces.

2. **A namespace is per-user or shared, and every access to it passes the matrix and the gate.** Each memory lives in a namespace and carries its tags. A namespace may be scoped to one user or shared across users and agents. **Reading, writing, and pruning a namespace each need a grant on it and pass the gate** (ADR-0005 point 2: an action passes both the matrix and ADR-0004's gate), so a write into a shared namespace, and the cleanup tool's deletion (point 5), are bounded exactly as a read is. A **per-user namespace** grants, by default, the user (a subject in their own right, ADR-0012 point 1) and that user's orchestrator (ADR-0040); it is not narrowed to the orchestrator's own row. A task-agent reaches it only through its template's declared access (ADR-0041 point 3), not as a separate default grant, so an instance's grants have one route, not two. ADR-0012 point 2's default-deny holds throughout, so a shared namespace grants no blanket access.

3. **The simple first implementation needs no external dependency, and is node-local for now.** The first backend is a local store pao can run on its own, a filesystem plus a simple index, enough to store, tag, namespace, and retrieve. On its own it is pinned to one node, since ADR-0013 point 4 keeps per-agent data local to its node; cross-node addressing is part of the plane's contract that this first store does not yet meet and declares so (ADR-0039's declare-so stance). Per ADR-0039, a mature external memory backend, for example Honcho, may replace it behind the same interface as configuration, never baked into the core, and this ADR names none as mandatory. Each backend passes the plane's contract test. **Plane 2 does not reopen the backend's own memory beyond what ADR-0025 already allows**: a backend's built-in memory stays off by default, opened only by a profile's per-category opt-in (ADR-0025 point 3), and a model or agent backend is not a memory driver.

4. **A run that resolved a secret does not write memory, for now.** A memory store is built to outlive the run and the instance (ADR-0041 point 2) and may be shared, so a secret written into it reaches the path ADR-0037 point 3 leaves open, and more durably than ADR-0042's working directory. As ADR-0042 point 5 did for the round-trip, this ADR gives an interim rule: **no memory writes from a run that resolved a secret**, until ADR-0037 point 3's item settles, which may later refine it.

5. **A cleanup tool runs over memory.** Memory accumulates, so the plane provides a cleanup tool that prunes or compacts it under rules, run on demand or on a schedule; a scheduled run, which has no requesting subject, runs under an existing subject configured for it, a human or an agent (ADR-0012 point 1), and is bounded by that subject's grant (point 2). Where ADR-0042's round-trip keeps history, memory needs the opposite pressure, a way to shed what is stale, so the two planes are deliberately asymmetric.

The internals left open: the retrieval semantics beyond a tag match (ranking, recency, scope precedence); **which namespace a template's memory lands in, derived from its tags**, settled with the tag-as-capability ADR, so this ADR **narrows** ADR-0041's per-user-or-shared question, both kinds of namespace exist, without fixing the template's own namespace; **cross-node memory addressing**, which no accepted ADR provides today (ADR-0013 point 4 keeps per-agent data local and ADR-0017's transport is still proposed), so it stays open; the cleanup rules, their defaults, and which configured subject runs a scheduled cleanup; what belongs in a per-user memory namespace versus the orchestrator's vault (ADR-0040 point 3), the vault being the orchestrator's own working state it reads and writes directly, memory being the tag-keyed store agents and templates retrieve from; and the exact contract-test shape for a memory backend.

## Consequences

Memory becomes a swappable plane rather than a built-in: the same agents and templates run on a node-local filesystem store or a mature external backend by configuration, access is decided by namespace and filtered by tag, and reads, writes and pruning all pass the matrix and the gate, so memory follows the same grant discipline as every other resource. A cleanup tool keeps it from growing without bound. This **builds on ADR-0039** (plane 2 and the driver discipline), **ADR-0041** (a template carries memory, whose per-user-or-shared question this narrows), **ADR-0012, ADR-0005 and ADR-0004** (the namespace access model, and that reads, writes and prunes pass the matrix and the gate), **ADR-0040** (the per-user orchestrator, and the vault memory is kept distinct from), **ADR-0013** (per-agent data is node-local today), and **ADR-0037 and ADR-0042** (the secret-run interim rule); it supersedes none, and it leaves the tag's own definition to the next ADR.

The cost is a memory interface that must serve both a node-local store and a mature backend without leaking either's shape, keep the namespace the access unit while the tag only filters, and gate writes and prunes as well as reads. The mitigation is ADR-0039's simple-first discipline: prove the node-local filesystem store, access and all, before an external or cross-node backend is drawn.
