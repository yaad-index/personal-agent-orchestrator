# ADR 0038: A group's topics are conversations of that group

**Status:** Proposed

Supersedes ADR-0023 (agent I/O: channel bindings and the default agent). Keeps its points 1, 2 and 6 to 8 unchanged, and its deferred list except the item point 9 raised. Changes points 3 to 5, so that a conversation may have a default agent of its own, and replaces point 9: a topic of a topic-enabled group is a conversation of that group, not a channel. Decides two items on ADR-0028's deferred list, which ADR-0029 keeps: topics, and a group's own default agent. Extends ADR-0003, ADR-0008, ADR-0009, ADR-0012, ADR-0013 and ADR-0019, as ADR-0023 does, and builds on ADR-0028's group points and ADR-0029 (output routing).

## Context

Some platforms let a group be split into topics. Each topic is its own thread of messages inside the group, with its own place in the platform's interface. A topic is not a group of its own: on the platform the bot runs on today, a topic's messages carry the group's id and, beside it, the topic's id. A message sent with the group's id and no topic id lands in the group's general topic.

pao reads neither part of that today. It takes a group's conversation to be the group's id alone. So a message written in a topic is accepted as a message from its group, and the reply to it goes to the group's general topic, not the topic it was asked in. An agent cannot be bound to one topic, and an operator who sets an agent to answer in a topic sees its answers land somewhere else. Nor can a topic have an agent that answers plain text there: the default agent is per channel, so every topic, the group's own conversation and every private conversation share one.

ADR-0023 point 9 decided topics another way: each topic would be a channel. It also said what that costs. A channel is one adapter with its own receive loop, and a platform whose credential allows a single polling consumer cannot run one loop per topic. So N topic channels on one credential need one receiver dispatching to N channels, a change to the one-adapter-per-channel shape. ADR-0028 deferred topics for that reason, and a group's own default agent with them.

ADR-0029 has since made the conversation, not the channel, the thing output is routed to (point 1), and the thing a reply goes back to (point 2). A topic fits there with no change to the shape of channels: it is one more conversation of a channel, inside a group that is already one. That is what this ADR decides. Because it changes ADR-0023's points 3 to 5 and replaces its point 9, it supersedes ADR-0023 whole.

## Decision

ADR-0023's decision, restated whole so this record stands alone. Points 1, 2 and 6 to 8 are unchanged. Points 3 to 5 change by the parts marked **Changed**. Point 9 is replaced, and points 10 to 12 are new.

1. **An agent declares three I/O streams, by loose analogy to stdin / stdout / stderr.** The set is deliberately small and open to future extension.
   - **stdout** — output and its verbosity.
   - **stdin** — input.
   - **stderr** — the agent's own system/error line (config and permission-check notices).

2. **stdout is multiplexed to channels, each at its own verbosity level.** One agent's output may fan to several channels. Each binding carries a single level N, read against the profile's per-kind level map (ADR-0008 point 2): the channel shows every kind the profile places at or below N, so one channel sits at a basic level and another at full detail. The binding carries the level N, not a map of its own. A viewer's interactive backtrack (ADR-0008 point 3) still applies on top. Fanning a binding to a channel on another node is the cross-node output of ADR-0013 point 3.

3. **stdin is at most one input per agent, and the default-agent role (point 5) IS that binding.** An agent has at most one input bound. A channel's default agent (point 5) is exactly the agent bound to that channel as stdin. **Changed:** a conversation's default agent (point 5) is likewise the agent bound to that conversation as stdin. So an agent is the default of at most one channel or conversation; the two are one binding seen from each end, not two facts that can disagree. In addition, any chat may address the agent explicitly with a pao command (point 6). A channel or conversation bound as stdin may also be one of the agent's stdout destinations: input and output in the same place.

4. **An agent is routed to by a precedence of signals, default last.** An inbound in a channel may carry several routing signals; they resolve in order: an **explicit** target (point 6) first; then a **reply** to an agent's message, routed to that message's author; then the sender's **sticky** last explicit target, which the adapter keeps; and only when none of those is present, the **default agent**. **Changed:** the default is the conversation's own, if it has one (point 5), and otherwise the channel's. This is the destination-selection for input that names no target, which ADR-0003 deferred.

5. **A channel has a default agent, and so may a conversation; the default answers the no-target case unprefixed.** When the precedence of point 4 falls through to the default, the message routes to the default agent. The default agent's output carries no `[name]:` prefix — it reads as the channel's natural voice; an explicitly addressed, non-default agent's output is prefixed `[name]:`. The default is a single agent **by name, not a tag**, because a tag names a group. The operator switches a default with a pao command. **Changed:** an admitted group (ADR-0028 point 1) or a named topic (point 10) may have a default agent of its own, which comes before the channel's. A message in the group's own conversation goes to the group's default, a message in a named topic to that topic's, and a message in a topic that isn't named to its group's. Where the conversation has none, the channel's default answers, as before. A conversation's default is set and cleared like a channel's, at the operator surface and by a steering command from chat (ADR-0026). A node that sets no conversation default routes exactly as it did.

6. **Addressing an agent is a pao command, not a platform mention.** `/pao` is pao's command prefix; an agent is addressed as `/pao agent <name> <message>`. A platform's own mention syntax is not reused, to avoid clashing with it. **Tag addressing is retained**: addressing by tag (ADR-0003 point 2, ADR-0012 point 4, fan-out bounded by access) stays available from chat through `/pao`; only the *default-agent* role (point 5) excludes tags. The exact tag form and a shorthand for the whole command are wanted and deferred.

7. **stderr is per-subject; a denial notice and an approval question are split.** An agent's own config and permission-check **notices** (e.g. "you may not do that") go to the subject who caused them, on the channel that subject's causing inbound arrived on (ADR-0019 point 4 lets a subject have bindings on several channels). An **approval question** (ADR-0004) is not an stderr notice to that subject: it must reach whoever may answer it — the operator — never a non-operator subject. So a denial is addressed to the subject, an approval prompt to the operator.

8. **A channel is a resource in the access matrix; one channel, many subjects (ADR-0012).** A channel (stdin and/or stdout) is a resource row, and any subject with access may use it. pao attributes each inbound to its subject (ADR-0019) and gates per message, so isolation comes from the matrix, not from a separate bot or front per subject. This decides what a channel grant means for a human beyond a front they may use, which ADR-0012 left open: a channel is a resource any granted subject may use for stdin and/or stdout.

9. **Replaced: a topic is a conversation of its group, not a channel.** A message written in a topic belongs to that topic's conversation, named by the group's id and the topic's id together. A message in a group without topics, or in a topic-enabled group's general topic, belongs to the group's own conversation, exactly as before. The adapter treats a message as a topic's only where the platform marks it as written in a topic. A platform may attach a thread id to other messages, such as a reply inside a group without topics. That id does not make a topic, and such a message is the group's as before. A private conversation has no topics and is unchanged. ADR-0023's design, one channel per topic over one receiver, is withdrawn: the platform's single polling consumer stays one adapter serving one channel.

10. **New: every topic of an admitted group is served, and a topic the operator names is a destination.** Admitting a group (ADR-0028 point 1) serves every topic in it, as it does today. A topic has no member policy of its own: its readers are its group's, so the narrowest-reader rule (ADR-0028 point 5) is the same for a topic as for its group. A topic whose group is not admitted is refused, as its group is. A group's admission may also name some of its topics, each by the platform's topic id and a name of its own, unique among the node's groups and topics. A named topic is a destination, `group:<name>` as ADR-0029 point 1 names a group, so a standing binding or a default (point 5) can point at it. A topic that isn't named is still its own conversation for replies (point 11) and the last address (point 12); it just can't be set as a destination. Naming topics is administration at the operator surface, like admitting the group. When the platform moves a group to a new id (ADR-0028 point 1), its named topics are unlisted with it, and are named again when the operator lists the new id.

11. **New: a reply goes back to the topic it was asked in.** ADR-0029 point 2 applies to a topic as to any conversation: a message from a topic notes that topic as the origin, and the agent's output in that turn is sent into the topic. A standing binding to a topic (ADR-0029 point 3) sends into that topic. A command's answer and a button press (ADR-0026, ADR-0027) are a topic's when they come from it. A group's own conversation is sent to as before, with no topic named, so it lands in the general topic.

12. **New: a sender's last address is kept per conversation, and so per topic.** ADR-0028 point 4 keeps the sticky target of point 4 per sender and per conversation. A topic is a conversation, so an address made in one topic does not steer what the same person types in another topic, in the group's own conversation, or privately.

## What this ADR deliberately does NOT decide

Carried over from ADR-0023, unchanged: the config schema for the bindings; the verbosity level numbers (ADR-0008 left them open); the exact tag-addressing form and the shorthand for `/pao agent <name>`; whether a channel's default agent is set at channel creation or only later; the migration path from a single-agent deployment; and whether stderr's system channel is a distinct channel kind or a reserved per-subject binding. ADR-0023's item on the single-receiver-serving-many-channels adapter shape is dropped, because point 9 no longer needs one.

New:
- **A member policy per topic.** A topic is read by its group's readers. A topic admitted to fewer or other people than its group would need the platform to keep them out, and pao cannot see who the platform shows a topic to.
- **Creating, renaming or closing topics.** That is the platform's, and the operator's in the platform. pao reads the topic id it is given and does not follow a topic's name.
- **Topics on other platforms.** Points 9 to 12 are written against the shape described in Context: a topic id beside the group id on each message, and a send that names the topic. A platform that models threads differently gets its own decision when its adapter is built.

## Consequences

Carried over from ADR-0023: a single-agent deployment keeps every channel and gains explicit, per-channel control over which agent answers, where its output goes, and at what verbosity, with more agents addable without losing the single-agent experience — so the configurable model is a superset of it rather than a replacement that drops capability. A channel's default agent makes the common case (talk to the one agent that owns this channel) need no prefix or command, while naming an agent or a tag stays available everywhere. Making channels resources in the access matrix keeps multi-human scoping (ADR-0012) coherent with the I/O model; routing a denial to the subject but an approval question to the operator keeps the gate answerable while keeping one subject's notices off another's view.

Changed: a platform whose direct chat is a single conversation gets several places to talk through a group's topics with no change to the shape of channels and no second receiver. An operator can give each topic of one group its own agent, for output, replies and plain text, without a second bot or a second group. A group without topics, and every private conversation, behave as before; the build's tests hold both as invariants. The adapter's id for a conversation grows a second part, so each place that reads it (sending, replies, button presses, the last address and the record of a moved group) changes with it. A default can now live in two places. The precedence stays one ordered list, and the channel's default remains the last step.
